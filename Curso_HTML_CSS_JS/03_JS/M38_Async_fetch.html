Async: promesas y fetch

Las llamadas a la red, los timers, la lectura de ficheros... nada de eso es instantáneo. Tu código tiene que esperar, pero sin bloquear la página. Aquí entran las promesas, async/await y el patrón fetch.

Event loop async/await fetch (mock sin red)
1 El event loop: por qué JS no se bloquea

JS es single-threaded: solo ejecuta una cosa a la vez. Pero el navegador hace mucho a la vez: renderiza, escucha eventos, hace peticiones. El event loop es el bombero que organiza la cola: el código síncrono va primero, las microtareas de las promesas van después, las macrotareas (timers, I/O) van al final.

JavaScript · orden de ejecución 
console.log('1 síncrono');

setTimeout(() => console.log('4 macrotarea (timer)'), 0);

Promise.resolve().then(() => console.log('3 microtarea'));

console.log('2 síncrono');

// Salida: 1, 2, 3, 4
2 Promesas: el "esto después" tipado

Una promesa es un objeto que representa un valor que estará disponible en el futuro. Tiene tres estados: pendiente, cumplida (con un valor) o rechazada (con un error). Una vez resuelta, no cambia.

pendiente → cumplida ✓ | rechazada ✗
JavaScript · crear y consumir una promesa 
// Crear
const p = new Promise((resolve, reject) => {
  setTimeout(() => {
    resolve('¡Listo!');    // o reject(new Error('falló'))
  }, 1000);
});

// Consumir con .then/.catch/.finally
p
  .then(valor => console.log(valor))
  .catch(err => console.error(err))
  .finally(() => console.log('terminó'));
3 async/await: promesas con sintaxis de función

async marca una función como asíncrona (siempre devuelve una promesa). await espera a que una promesa se resuelva, sin bloquear el hilo principal. El código se lee como si fuera síncrono, pero no lo es.

JavaScript · async/await 
async function cargarUsuario(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error('HTTP ' + res.status);
    const user = await res.json();
    return user;
  } catch (e) {
    console.error('No pude cargar:', e.message);
    throw e;  // re-lanza para que el caller decida
  }
}

Combinadores: Promise.all, race, allSettled

Promise.all
Promise.all([p1, p2])
Espera a todas. Si cualquiera falla, todo falla. Para tareas en paralelo que se necesitan juntas.
Promise.race
Promise.race([p1, p2])
Gana la primera que termine (éxito o error). Útil para timeouts: race([fetch, timeout(5000)]).
Promise.allSettled
Promise.allSettled([...])
Espera a todas y devuelve {status, value|reason} por cada una. Nunca falla. Para tolerar fallos parciales.
4 fetch: la API moderna para red

fetch(url) devuelve una promesa que se resuelve en un objeto Response. Punto crítico: fetch solo rechaza la promesa por errores de red, no por códigos HTTP 4xx/5xx. Por eso el patrón canónico es if (!res.ok) throw new Error('HTTP ' + res.status).

JavaScript · el patrón canónico 
const res = await fetch('/api/users');
if (!res.ok) throw new Error('HTTP ' + res.status);
const data = await res.json();   // otra promesa

POST con body JSON

JavaScript · POST 
const res = await fetch('/api/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Ana', email: 'a@x.com' })
});
5 En la vida real (caja teórica)

Este curso no usa red real por seguridad. Pero cuando salgas al mundo, estos son los conceptos que te encontrarás:

Conceptos de fetch en producción

  • CORS (Cross-Origin Resource Sharing): por seguridad, el navegador bloquea peticiones a otros dominios. El servidor debe enviar la cabecera Access-Control-Allow-Origin para permitirlo.
  • Cabeceras: Authorization: Bearer <token> para autenticación, Content-Type: application/json para el cuerpo.
  • OPTIONS preflight: las peticiones "complejas" (con cabeceras custom, no GET) hacen primero un OPTIONS que el servidor debe aprobar.
  • Response.status: 200 OK, 201 creado, 400 error del cliente, 401 sin auth, 404 no existe, 500 error del servidor.
  • El if (!res.ok) sigue siendo obligatorio aunque la promesa no haya rechazado.
6 fakeFetch: la API mock del curso

En este curso fetch está parcheado. Hay un fakeFetch que lee JSONs embebidos arriba en este mismo HTML, modela tanto éxito (200) como fallo (404) y errores de red. El patrón que escribes es el mismo que en producción.

JavaScript · fakeFetch (definido al final de este HTML) 
function fakeFetch(url) {
  // Busca un <script type="application/json" id="..."> que coincida con la URL
  const id = 'api-' + url.replace('/api/', '');
  const raw = document.getElementById(id);
  if (!raw) return Promise.reject(new Error('Network error: 404'));
  const mock = JSON.parse(raw.textContent);
  return Promise.resolve({
    ok: mock.ok, status: mock.status, statusText: mock.statusText || 'OK',
    json: async () => mock.data,
    text: async () => JSON.stringify(mock.data)
  });
}
