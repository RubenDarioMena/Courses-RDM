Buenas prácticas y debugging

Un programa que "funciona" en tu máquina puede romperse en producción. La diferencia entre un dev junior y uno senior no es la cantidad de bugs: es la velocidad con la que los encuentra y la disciplina con la que los evita. Aquí te llevas las dos cosas: el cinturón de seguridad y las herramientas para cuando algo se sale del carril.

1El cinturón antes de la moto

Estilo, linter y formateador

Escribir código que funciona es la mitad del trabajo. La otra mitad es que se pueda leer seis meses después por ti o por tu compañero. Tres herramientas te cambian la vida:

  • Guía de estilo: convenciones del equipo (nombres, indentación, comillas, etc.).
  • ESLint: analiza tu código y avisa de errores latentes (variables no usadas, == en vez de ===, imports rotos).
  • Prettier: reformatea tu código automáticamente al guardar. Cero discusiones sobre comas.

"use strict": el modo paranoico

Activar "use strict" al inicio de un script (o en una función) convierte errores silenciosos en excepciones. Prohíbe variables sin declarar, this accidental en undefined, y un puñado de trampas históricas. Es un interruptor de seguridad gratuito; actívalo siempre.

ESLint
Analiza tu código estáticamente. Te avisa de variables no usadas, comparaciones sospechosas, imports que no existen.
Prettier
Formatea al guardar. No discute: siempre la misma indentación, comas y comillas. Se integra con VS Code.
"use strict"
Convierte errores silenciosos en excepciones. Añádelo al inicio de cada script o módulo.
typecheck (TS)
Si quieres el siguiente nivel: TypeScript te avisa de errores de tipo antes incluso de ejecutar.
2El debugger: pausar el tiempo

Breakpoints: donde la ejecución se detiene

Un breakpoint es un semáforo rojo en una línea de código: cuando la ejecución llega ahí, se pausa y puedes inspeccionar variables, el call stack y el estado del DOM. Se pone con un clic en la pestaña Sources de DevTools o con la palabra clave debugger; directamente en tu código.

Step over · step into · step out

  • Step over (F10): ejecuta la línea actual y pasa a la siguiente. Si la línea llama a una función, no entras: la ejecuta del tirón.
  • Step into (F11): si la línea llama a una función, entras dentro de ella. Ideal cuando sospechas que el bug está en una sub-rutina.
  • Step out (Shift+F11): termina la función actual y vuelve a quien la llamó.
Bug intencionado + debugger 
// ⚠️ "use strict" activado
"use strict";

function promedio(numeros) {
  // 🐛 BUG: si el array está vacío, .reduce explota
  debugger;  // abre DevTools para pausar aquí
  const suma = numeros.reduce((a, b) => a + b, 0);
  return suma / numeros.length;
}

// En un fix robusto haríamos:
// if (!numeros.length) return 0;

try {
  const usuarios = [];  // array vacío simula el bug
  console.log('promedio:', promedio(usuarios));
} catch (e) {
  console.error('nombre:', e.name);
  console.error('mensaje:', e.message);
  console.error('stack:', e.stack.split('\n')[0]);
}

3Console avanzado

Más allá de console.log

La consola tiene muchas más herramientas que log. Conocerlas te ahorra formatear strings a mano y te da información que un simple log jamás podría mostrar.

console.table · group · time 
// console.table: array de objetos → tabla interactiva
const usuarios = [
  { nombre: 'Ada',  edad: 36, rol: 'admin'   },
  { nombre: 'Lin',  edad: 28, rol: 'editor'  },
  { nombre: 'Nik',  edad: 42, rol: 'viewer'  }
];
console.table(usuarios);

// console.group: jerarquiza mensajes relacionados
console.group('Carga de datos');
  console.log('1. fetch iniciado…');
  console.log('2. JSON parseado');
  console.groupCollapsed('detalles');
    console.log('3.1 url: /api/usuarios');
    console.log('3.2 tamaño: 1.2 KB');
  console.groupEnd();
  console.log('4. UI renderizada');
console.groupEnd();

// console.time: medir duración
console.time('parse-json');
const big = JSON.parse(JSON.stringify(usuarios));
console.timeEnd('parse-json');

4Estrategias para encontrar bugs

El método que funciona siempre

  • Reproduce el bug en el caso más simple posible. Si puedes aislarlo a 5 líneas, lo encontrarás.
  • Lee el stack trace de abajo arriba: la primera línea es donde el programa reventó; las anteriores muestran cómo llegó ahí.
  • Divide y vencerás: comenta bloques hasta que el bug desaparezca. La última línea que comentaste es la culpable.
  • Rubber duck: explica el código en voz alta a un objeto inanimado. Suena ridículo. Funciona el 70% del tiempo.
  • Hipótesis, no adivinanzas: no toques código sin una teoría previa. Si tu teoría falla, tienes un dato nuevo: lo que NO está roto.
Cómo leer un stack trace 
function a() { b(); }
function b() { c(); }
function c() { throw new Error('algo falló'); }

try { a(); }
catch(e) {
  console.log('--- stack ---');
  console.log(e.stack);
  console.log('--- primera línea = sitio exacto ---');
  console.log(e.stack.split('\n')[0]);
}
