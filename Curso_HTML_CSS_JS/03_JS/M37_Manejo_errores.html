MÓDULO 37 · ERRORES

Manejo de errores

Todo falla. Siempre. La pregunta no es si tu código fallará, sino qué pasa cuando falle. try...catch es el cinturón de seguridad: no evita el accidente, pero evita que la página explote en la cara del usuario.

try / catch / finally throw new Error ~15 min de lectura
1 try / catch / finally

Tres bloques. try ejecuta el código peligroso. Si lanza un error, catch lo atrapa (y tu script sigue vivo). finally corre siempre, haya error o no — perfecto para limpiar.

JavaScript · try / catch / finally 
try {
  const data = JSON.parse(userInput);
  render(data);
} catch (err) {
  console.error('JSON malformado:', err.message);
  showUserFriendlyError();
} finally {
  hideLoadingSpinner();  // SIEMPRE se ejecuta
}
2 throw new Error: lanza tus propios errores

No esperes a que JS lance un error. Si una precondición no se cumple, tú mismo lo lanzas con un mensaje claro. Usa el tipo de error que mejor describa el problema.

Error
throw new Error('msg')
Genérico. Úsalo cuando ninguno de los específicos encaje.
TypeError
throw new TypeError(...)
Tipo incorrecto: pasaste un número donde va un string, leíste null.foo, etc.
RangeError
throw new RangeError(...)
Valor fuera de rango: índice de array negativo, número fuera de los límites esperados.
SyntaxError
throw new SyntaxError(...)
Texto malformado: JSON corrupto, regex inválida, código que no parsea.
JavaScript · throw con tipos 
function dividir(a, b) {
  if (b === 0) throw new RangeError('División por cero');
  if (typeof a !== 'number' || typeof b !== 'number')
    throw new TypeError('Ambos argumentos deben ser números');
  return a / b;
}

try { dividir(10, 0); }
catch (e) {
  console.error(e.name, e.message);  // "RangeError" "División por cero"
}
3 Leer un stack trace

Cuando algo falla en consola, ves un stack trace: una lista de llamadas que llevó al error. Se lee de arriba (donde saltó) hacia abajo (la llamada inicial). Cada línea dice archivo, función y número de línea.

Consola · ejemplo de stack trace 
TypeError: Cannot read properties of null (reading 'foo')
    at handleClick (app.js:42:17)       // ← aquí saltó
    at HTMLButtonElement.<computed> (app.js:88:5)  // ← quien lo llamó
    at HTMLButtonElement.dispatchEvent          // ← evento del DOM

La línea superior es donde el error saltó. Las inferiores son la cadena de llamadas que llevó ahí. En M43 profundizaremos en el debugger visual de DevTools.

4 Estrategias: cuándo capturar y cuándo no

Antipatrón: un catch(e) {} vacío se traga el error y tu script sigue como si nada. Bugs invisibles. Si vas a capturar, haz algo: log, mensaje al usuario, re-throw.

Validación temprana > catch

Es mejor prevenir el error que atraparlo. Si una función espera un email, valida el formato antes de procesar. try...catch es el cinturón, no el parche.

Errores asíncronos (intro)

try...catch no atrapa errores dentro de callbacks ni de promesas. Para eso existen .catch() en promesas y try/catch con async/await. Lo verás en detalle en M38.
